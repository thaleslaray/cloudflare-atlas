# D1 — serverless SQLite database (scale-to-zero, query from Workers)

> Cloudflare's managed serverless SQL database with SQLite semantics, built-in disaster recovery,
> and zero egress fees. Query directly from Workers via a binding. Billed only on usage + storage.

## When to use
- Relational data with SQL: app data, sessions, multi-tenant SaaS, metadata, small analytics.
- You want a **native, scale-to-zero** SQLite DB queried from a Worker with no connection pooling.
- **Per-tenant / per-user databases**: thousands of small DBs at no extra cost (horizontal scale-out).
- Pairs with: Workers (compute), KV (cache hot rows), R2 (store blobs/files — keep only keys in D1).
- Migrating FROM Supabase/Postgres INTO D1: no official path (docs: Postgres dumps cannot be
  imported). Use the `supabase2d1` skill if installed. Gotcha if converting by hand: `sqlite3 .dump`
  (CLI 3.50+) emits `unistr()`, which D1 lacks — generate import SQL via Python `iterdump()`.
- **Not** for: connecting to an **existing Postgres/MySQL** (→ **hyperdrive**), key-value (→ kv),
  large objects/files (→ r2), vector search (→ vectorize). Single DB caps at **10 GB** — design to shard.

## Binding & config (`wrangler.jsonc`)
```jsonc
{
  "d1_databases": [
    { "binding": "DB", "database_name": "my-db", "database_id": "<uuid>",
      "migrations_dir": "migrations" }
  ]
}
```
Access in Worker: `env.DB.prepare(sql)`. Create/migrate via CLI: `wrangler d1 create my-db`,
`wrangler d1 migrations apply my-db --remote` (the `--remote` flag is required for production —
without it you only touch the local SQLite file).

## Prepared statements & batch
```ts
// ALWAYS bind params — never string-interpolate (SQL injection).
const u = await env.DB.prepare('SELECT * FROM users WHERE id = ?').bind(id).first();
await env.DB.prepare('INSERT INTO users (name,email) VALUES (?,?)').bind(name, email).run();
const { results } = await env.DB.prepare('SELECT * FROM posts LIMIT ?').bind(50).all();

// batch() = one round trip, runs as an implicit transaction (all-or-nothing):
const [users, posts] = await env.DB.batch([
  env.DB.prepare('SELECT * FROM users WHERE id = ?').bind(id),
  env.DB.prepare('SELECT * FROM posts WHERE user_id = ?').bind(id),
]);
```
Methods: `.first()` (one row), `.all()` (rows + `meta`), `.run()` (write, returns `meta`),
`.raw()` (arrays). Every result `meta` carries `rows_read` / `rows_written` (= your bill).

## Gotchas
- **Bind, don't interpolate** — string SQL = injection. Use `?` placeholders + `.bind()`.
- **`--remote` flag**: migrations/queries default to a *local* DB; production needs `--remote`.
- **No native BOOL/DATE**: store booleans as `0/1`, dates as TEXT (ISO 8601) or INTEGER (unix).
- **Index your filters**: unindexed `WHERE` does a full scan → high `rows_read` (= cost + slow).
  Check with `EXPLAIN QUERY PLAN`; add `CREATE INDEX`.
- **Single-threaded per DB**: throughput ≈ 1/query-duration. Avoid N+1 — use JOIN or `batch()`.
- **Big mutations fail**: docs — "A single query that attempts to modify hundreds of thousands of
  rows or hundreds of MBs of data at once will exceed execution limits" (30 s max query duration).
  Chunk into batches (~1,000 rows).
- **Read replicas**: no extra charge (same `rows_read`/`rows_written` billing); enabled per database
  (dashboard Settings, or REST `read_replication.mode: auto`). A replica "may be arbitrarily out of
  date" — docs publish no lag number. Use the **primary** (or Sessions API bookmarks) for
  read-after-write/auth/payments.

## Pricing & limits
> ⚠️ Pricing changes — verify on the live page (`developers.cloudflare.com/d1/platform/pricing/`) before quoting.

**Cost drivers** (Workers Paid, as of 2026-06): scale-to-zero — no compute/capacity charge.
- Rows read: first **25 B/mo** included, then **$0.001 / million**
- Rows written (INSERT/UPDATE/DELETE): first **50 M/mo** included, then **$1.00 / million**
- Storage: first **5 GB** included, then **$0.75 / GB-month** (sum of all DBs in account)
- **Egress: FREE.** Indexes reduce rows read but add ~1 row written per indexed write.
- **Free plan**: 5 M rows read/day · 100 K rows written/day · 5 GB total storage (resets 00:00 UTC).
- **Since 2026-09-01 the free daily limits are ENFORCED, not just billed against.** Past the daily
  row-read or row-write cap, queries **fail** — Workers Binding API and REST API both return
  `Your account has exceeded D1's free tier daily row read limit…` (same wording for writes) until
  midnight UTC. Stored data is untouched and email alerts fire on the cap. Before this, exceeding
  the free tier degraded nothing. If you ship on Free, add indexes and kill full table scans, or
  the app hard-stops mid-day.

**Key limits** (Paid / Free): max DB size **10 GB** / 500 MB (Paid cap cannot be raised) · storage/account 1 TB / 5 GB
· DBs/account 50,000 / 10 (raisable) · queries per Worker invocation 1,000 / 50 · row/string/BLOB
**2 MB** · SQL statement **100 KB** · bound params **100** · columns/table **100** · query duration
**30 s** · args per SQL function **32** · LIKE/GLOB pattern **50 bytes** · Time Travel restores 10 per
10 min/DB · file import (`d1 execute`) 5 GB · ≤6 simultaneous D1 connections per invocation. Time Travel
PITR 30 d / 7 d. Verify on `developers.cloudflare.com/d1/platform/limits/`.
